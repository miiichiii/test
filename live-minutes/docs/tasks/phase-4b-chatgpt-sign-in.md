# Phase 4B: ChatGPT でのログイン

## 目的

API キーの代わりに、ChatGPT の有料プランの利用枠で OpenAI を使えるようにする。API キーの方式は残し、設定画面で選べるようにする。

Phase 4 の後に追加したフェーズ。Phase 5 の前でも後でも行える。番号は順序を表すだけ。構造化出力がプランで使えるか（DESIGN.md §8 #9）で後半の前提が変わるので、4B-1 と 4B-2 に分け、間に人による確認を挟む。

## 先に読むもの

- [AGENTS.md](../../AGENTS.md)（特に「新しいAPIの扱い」「秘密情報」）
- [DESIGN.md](../DESIGN.md) §4.7（LLM）、§4.8（Settings）、§4.11（ChatGPT でのログイン）、§5（画面）

## 4B-1: 認証とクライアント

### 作業内容

1. `LLM/`
   - `LLMCredential`、`CredentialProvider`、`CredentialRouter`
   - `OpenAIResponsesClient`
     - API キーの読み出し関数の代わりに `CredentialProvider` を受け取る。資格情報を先に取得し、それに合わせてボディを組み立てる
     - ChatGPT プランのときは、構造化出力もストリーミングで送り、`response.completed` まで差分をためてから読む
     - `input` を配列にそろえる
     - 401 を受けたら、失敗した資格情報を渡して `CredentialProvider` に知らせ、true が返れば1回だけ送り直す（今の再試行の回数とは別に数える。資格情報の種類が変わっていたら送り直さない）
     - ChatGPT のときに `param` が `reasoning` で始まる 400 を受けたら、`reasoning` を外して1回だけ送り直し、そのプロセスの間は外したままにする
   - `error.code` から `LLMError` への対応付けを1つの関数にし、HTTP・`response.failed`・`error` イベントで共有する。DESIGN.md §4.11 のエラーの表のとおりにする
   - `LLMError` に、使用量の上限・要ログイン・プランの対象外・使えないパラメータを足す。認証エラーの文言を資格情報の種類ごとに分ける
   - モデル一覧（`GET /v1/models`。`models` 配列の `visibility == "list"`）
2. `Settings/`
   - `ChatGPTAuth`（actor）: ログイン、キャンセル、ログアウト（取り消しを含む）、トークンの更新（1本にまとめ、待つ側のキャンセルで打ち切らない）、ID トークンの検証（JWKS の RS256）、状態、世代
   - トークンの保存先（protocol。キーチェーン版とメモリ版）。API キーとは別の項目にし、書き換えは `SecItemUpdate` を先に試す
   - ホストIDの保存（`UserDefaults`）
   - `LoopbackCallbackServer`（`127.0.0.1` だけで待ち受ける）
   - form と URL の自前のエンコード
   - `AppSettings.authMethod`
   - `ConnectionTest`: ChatGPT のときは、モデル一覧に設定したモデルIDがあるかも表示する（一覧の失敗でテスト全体を失敗にしない）
3. 設定画面: 「接続方法」、ログイン・キャンセル・ログアウト、ログイン後の表示（メールアドレス、「ChatGPT プランを使用中」、「使用量を管理」）
4. `SessionController.apiKeyDidChange()` を `credentialsDidChange()` に改め、ログイン・ログアウト・接続方法の変更でも呼ぶ（ライブ更新の扱いは 4B-2 で仕上げる）
5. entitlements に `com.apple.security.network.server` を足す

### テスト（実際の OpenAI には接続しない。`URLProtocol` のスタブと偽物を使う）

- 認可 URL: 初回と2回目以降の違い（`agent_name_hint`、`id_token_hint`）、PKCE の値、`login_hint` を送らないこと
- form と URL のエンコード: `+`・`&`・`=`・`/` を含む値
- コールバック
  - `state` の不一致には 400 を返して待ち続けること
  - `access_denied` で終わり、何も保存しないこと
  - `client_id` の不一致を拒否すること。初回で `client_id` がない場合に保存しないこと
  - 決めたパス以外への要求に 404 を返すこと
  - 成功の後に `/auth/done` へ 302 で移すこと
- ループバックの待ち受け
  - 実際に `127.0.0.1` へ要求を送り、コードを受け取れること（ポートは OS に選ばせ、1455 は使わない）
  - 使用中のポートから、OS に選ばせるポートへ切り替えること
  - 分割して届く要求、何も送らない接続、16KB を超える要求
  - キャンセルと5分の打ち切りで、何も保存しないこと
- コードの交換と ID トークン
  - `iss`・`aud`（文字列と配列）・`exp`（60秒の許容の前後）・`nonce` のそれぞれの不正
  - 署名の検証: 正しい署名、署名の不正、知らない `kid`（1回だけ取り直す）、`alg` が `none` や HS256。鍵はテストの中で `SecKeyCreateRandomKey` で作る
  - `chatgpt.tokens.use.direct` が付与されなかった場合と、`scope` が応答にない場合
  - 保存済みの `client_id` で `sub` が違う場合に拒否し、何も保存しないこと
- トークンの更新
  - 期限の5分前からの更新。期限の判定が壁時計であること
  - 同時の要求が1本にまとまること
  - 待つ側がキャンセルされても、更新が最後まで走って保存されること
  - ローテーションした値の保存。保存に失敗してもメモリで使い続けること
  - 終端のエラーで要ログインになり、`client_id` と `sub` が残ること
  - キーチェーンに新しいトークンがある場合、再利用のエラーで消さずにそれを使うこと
  - 通信エラーではトークンを捨てないこと。`invalid_client` ではログインし直させないこと
  - キーチェーンを読めない場合に、上書きも削除もしないこと
- ログアウト: 取り消しの成功、5xx の再送、確かめられなかった場合、更新中のログアウト（更新の完了を待ってから最新のトークンを取り消す）
- リクエスト
  - ChatGPT のときに `stream: true`・`store: false`・配列の `input` になること。API キーの構造化出力はストリーミングにならないこと
  - 構造化出力をストリームから組み立てること。途中で切れた場合の再試行
  - 401 で1回だけ更新して送り直すこと。更新後にまた 401 でもトークンを捨てないこと
  - `reasoning` の 400 で、外して1回だけ送り直すこと
- エラーの表の各コード（HTTP とストリームの途中の両方）、`{"detail": …}` の本文、コードのない 401 / 403 / 503
- トークン、コード、検証子がログに出ていないこと（ログを出す箇所の確認）

### 受け入れ条件

- ビルドとテストが通る
- 自動テストが、実際の OpenAI（API と auth.openai.com）に接続していない
- トークン、認可コード、PKCE の検証子が、キーチェーン以外（`UserDefaults`、ファイル、ログ）に書かれていない。URL に載るのは、プロトコルで決まっているもの（コールバックの `code` と、認可の `id_token_hint`）だけ。ホストIDは秘密ではないので `UserDefaults` に置く
- API キーの方式が、これまでどおり動く（Phase 3・4 のテストが通る）
- DESIGN.md §8 の #9〜#12 に、確認した結果か「未確認」が書かれている

### 人が確認する項目

- 設定画面で「ChatGPT プラン」を選び、「ChatGPT で続ける」を押すと、既定のブラウザでログイン画面が開く。ログインして許可すると、アプリにメールアドレスが表示される
- 接続テストが成功する（§8 #9・#10 の確認。失敗したら、表示された理由を記録する）
- 1455 番のポートが使用中のとき（Codex CLI のログイン中など）でもログインできる（§8 #12）
- 「使用量を管理」を押すと、ChatGPT の使用量の画面が開く（§8 #11）
- アプリを終了して起動し直しても、ログインが保たれている。ビルドし直した後は、キーチェーンの許可ダイアログが出ることがある
- ブラウザの許可の画面で拒否すると、アプリに理由が出て、何も保存されない
- プランの利用を許可しなかった場合、「もう一度ログインして許可する」で同意の画面が出て、許可し直せる
- 「別のアカウントでログイン」で別の ChatGPT のアカウントに替えられる。「ChatGPT で続ける」で別のアカウントを選ぶと、理由が出て前のアカウントのまま
- API キーで使っている間は、起動しても ChatGPT のログインの情報のためのキーチェーンのダイアログが出ない
- 「ログアウト」の後は ChatGPT の設定の「接続済みのアプリ」からも消えている
- 接続方法を API キーに戻すと、これまでどおり API キーで接続テストが通る
- コンソール.app に、トークンやメールアドレスが出ていない

## 4B-2: ライブ更新と画面

4B-1 の人による確認の結果を見てから始める。構造化出力が使えなかった場合は、ここに入る前に設計を見直す。

### 作業内容

1. `NotesEngine`: 新しいエラーの分類（503 系と一般の一時的なコードだけを送り直す。残りは止める）。ストリームの途中の `response.failed` で、発言を捨てないこと
2. `LiveNotesFactory`: 「設定済みか」を接続方法ごとに判断する。未設定の案内の文言を接続方法ごとに分ける
3. 会議中の接続方法の切り替え（エンジンは作り直さず、`credentialsDidChange` から `retryNow`）
4. 画面（DESIGN.md §5）
   - ノートペインのヘッダの「ChatGPT プランを使用中」と「使用量を管理」
   - 使用量の上限、要ログイン、プランの対象外の案内
   - 最初のログインのときの案内（1回だけ）

### テスト

- 新しいエラーごとの `NotesEngine` の分類と状態
- ストリームの途中の `response.failed`（`server_error` など）で、バッチが捨てられないこと
- 会議中の接続方法の切り替えと、ログイン・ログアウトでの再開と停止
- 接続方法ごとの「設定済みか」の判断

### 受け入れ条件

- ビルドとテストが通る
- LLM の失敗が録音と文字起こしを止めない（ChatGPT の経路でも）

### 人が確認する項目

- 最初のログインのときだけ「ChatGPT プランを使います」の案内が出る
- 会議を開始すると、ノートペインに「ChatGPT プランを使用中」が出て、ノートが増えていく
- 1時間以上たってから会議をしても、ログインし直さずに使える（トークンの更新）。スリープから復帰した後も同じ
- 会議中に接続方法を切り替えても、文字起こしは止まらず、ノートは切り替えた方法で続くか、案内が出る
- デバッグ版とビルド済みの版を同時に起動しても、ログインが壊れない
